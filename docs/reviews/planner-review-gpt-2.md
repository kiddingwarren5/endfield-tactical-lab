**现有证据不足以支持“两段式更好”。更紧迫的是：实现存在缓存混淆、历史最优丢失、窗口末尾漏记未执行动作等错误，会影响搜索结果和诊断数据。应先修这些，再比较算法。**

**首先，以下问题应优先修复。**

1. **[P1] 缓存把不等价的同刻动作顺序合并了。**

   [search.js:11](/Users/serika/Developer/temp/endfield-demo-handoff-v3/dist/engine/sim/search.js:11) 的 `keyOf` 按时间、成员、类型排序；模拟器却保留同刻动作的输入次序，依次扣资源、触发效果。两者语义不一致。

   | 同刻输入次序 | 实际施放 | 得分 |
   |---|---|---:|
   | 祀 → 汤汤 | 祀 0 秒、汤汤 5.5 秒 | 16,274.3 |
   | 汤汤 → 祀 | 汤汤 0 秒、祀 5.5 秒 | 14,778.1 |

2. **[P1] 历史最优没有被完整保护，档案还有维护错误。**

   另外：

   - `offer` 更新同结构条目后不重新排序，`best()` 仍直接取 `archive[0]`。插桩确认出现了首项不是最高分的情况。
   - 精调会改变执行顺序，却不更新 `sig`。
   - 改善候选入档时，把 `plan` 换成规范化执行轨迹，却继续挂原候选的 `e`。原候选若有放弃动作，其惩罚也被带进了已删除这些动作的新计划。

   最小修改：维护独立的 `incumbent`，**每次真实评估后都更新**，包括初始化、重启、精调；档案只负责提供多样起点。规范化产生新计划时重新评估，或者证明变换保持执行与评分一致。档案更新统一走一个函数，重算签名、排序和去重。

3. **[P1] 窗口末尾未执行的动作被当成“零放弃”。**

   [simulate.js:316](/Users/serika/Developer/temp/endfield-demo-handoff-v3/dist/engine/sim/simulate.js:316) 只有重试超过 6 秒才记 `planSkip`；模拟到窗口结束时，尚在重试队列里的动作没有终态记录。

   | 请求时刻 | 执行次数 | `skipped` |
   |---|---:|---:|
   | 0 秒 | 0 | 1 |
   | 5 秒 | 0 | 0 |
   | 10 秒 | 0 | 0 |

   同样没有执行，后两者却不扣分，并被 `legalRatio` 算作合法。顺序表示也有类似问题：窗口结束时尚未处理的尾部，不计入 `seqSkip`。

   应给每个动作输出唯一终态，例如 `executed / expired / horizonCut / invalid`，并区分：

   - 请求计划是否完整执行；
   - 实际执行轨迹是否合法；
   - 有多少动作经过延迟、重排或删除。

   `errors.length===0` 或 `skipped===0` 都不足以回答这些问题。

4. **[P1] 总预算没有贯穿整条流程，评估次数上限也会突破。**

   [rotation.js:82](/Users/serika/Developer/temp/endfield-demo-handoff-v3/dist/engine/sim/rotation.js:82) 的束搜索没有时间或评估上限；最终每个候选的三次模拟也不计入搜索预算。退火首次评估发生在其计时器启动之前。局部搜索精调内层一次检查后可能再评估两个方向。

   探针中：

   - `maxEvals=250` 多次实际执行了 251 次；
   - `autoRotation` 设置 50 ms，小实例实际约 190 ms。这个数字不能推断正式预算的超时比例，但证明预算并非端到端约束。

   当前名义分配实际是：55.2% 退火、18.4% 时刻混合搜索、18.4% 逐动作精调；剩余 8% 没有形成束搜索与重放的硬预算。

   改法：入口建立共享的 `deadline`、`remainingEvals`，所有模拟统一经过一个计数入口；每次调用前检查。使用单调时钟，预留最终验证预算，并允许未耗完的阶段配额转给后续阶段。

5. **[P1/P2] 等待归一化和爆发目标各有一处明确语义错误。**

   [plan.js:78](/Users/serika/Developer/temp/endfield-demo-handoff-v3/dist/engine/sim/plan.js:78) 的 `normAct` 对等待只保留 `layers`，会丢掉 `seconds`。已复现：把 `wait(seconds:4) → 战技` 交给仅评估一次的退火，返回的是无条件等待，战技在 0 秒执行。现有测试只直接测 `evalSequence`，没有经过这个归一化入口。

   同时，`noHold:true` **仍然会生成层数等待**；它只是关闭 `minT` 变异。因此实验必须分别记录“是否允许 minT”和“允许哪些等待动作”。

   [plan.js:18](/Users/serika/Developer/temp/endfield-demo-handoff-v3/dist/engine/sim/plan.js:18) 只对 `cycle.complete` 的方案施加终结技分散惩罚；少放一个人的终结技，就可能完全逃掉惩罚。若这条路线确实要求四人集中爆发，应明确完整性约束；若只是鼓励某种搜索方向，应避免这种评分断点。

6. **“保底”的实际含义需要先裁定。**

   当前过滤掉了副控的直接普攻伤害，但[笔意记录逻辑](/Users/serika/Developer/temp/endfield-demo-handoff-v3/dist/engine/sim/simulate.js:146)仍记录副控普攻，随后作为战技伤害计分。

   同一个测试序列，仅把副控普攻伤害系数从 0.75 改为 0，所谓保底 DPS 就从 **31,373.9 降到 30,447.4**。

   当前指标准确的名字是“排除副控直接普攻后的伤害”。若要表达不依赖副控普攻，需要规定副控普攻及其触发效果的模拟场景，或者建立伤害来源归因。简单过滤最终命中标签无法得到严格下界，关闭副控普攻也不自动构成所有机制下的数学下界。

**实现采用了上一轮建议的外形，但几个关键机制还没有真正落地。**

| 部分 | 当前实现的差别与风险 | 可直接实施的改法 |
|---|---|---|
| 成组移动 | 按时间距离选取 ±3/±6 秒内所有动作，没有识别增益、附着、消费、记录之间的依赖。逐动作截断到窗口边界还会改变组内间隔。 | 日志增加 `castId/sourceId`；按依赖选 2–6 个动作联合移动。共同位移先求可行区间，保持相对时间。 |
| 破坏修复 | 删除随机片段后随机添加 1–4 个动作，实质是随机重建；没有利用被删动作的用途和片段边界状态。 | 保留候选动作集合，分别尝试原结构重排、替换一段依赖链、改变次数；每次限定 4–8 份重建候选，全部计费。 |
| 接受规则 | 只以 30% 概率接受下降不超过 1% 的新候选；更深的损失只能靠重启越过。阈值缺乏测量依据。 | 对照当前规则、按实测损失尺度校准的退火、阈值接受。记录接受损失分布及重启后的恢复时间；独立保护历史最优。 |
| 自适应权重 | 不看改善幅度和耗时；失败算子权重趋向 1，最好趋向 4，`0.2` 下限实际上不起作用。同分接受也得奖励。 | 按固定批次更新，记录新候选数、耗时、改善幅度和新历史最优次数；以单位耗时收益分配概率，另保留明确的均匀探索份额。 |
| 精英档案 | 相同动作顺序只留一个时刻版本，相当于假定同结构低分计划没有探索价值。这个假定不成立。 | 完整执行计划负责精确去重；每种结构保留少量不同时间区域的代表，例如不同增益覆盖、终结技轮数或记录结算位置。 |
| 精调 | 按动作依次单变量爬山，步长止于 0.2 秒；第一条精英可能耗尽全部预算。 | 给精英设置轮转配额，补 0.1 秒邻域和少量成组精调。每轮记录收益，动态决定是否继续。 |

当前主循环更接近“带重启的随机邻域搜索”。这本身可以有效，但还没有充分实现“扰动后进行局部改进”的 ILS 组织方式。对应上一轮“扰动＋局部改进＋接受规则”的建议：[Lourenço 等，2003](https://link.springer.com/chapter/10.1007/0-306-48056-5_11)。

同样，ALNS 文献支持让多个子启发式按历史表现竞争，不能替当前随机填充算子背书。“单位耗时收益”是针对本题预算提出的工程建议。对应上一轮“自适应算子”和“片段破坏修复”的建议：[Ropke & Pisinger，2006](https://pubsonline.informs.org/doi/10.1287/trsc.1050.0135)、[Godard 等，2005](https://cdn.aaai.org/ICAPS/2005/ICAPS05-009.pdf)。

**事件锚点尤其需要改成“对某个动作有意义的事件关系”。**

[anchorsOf 与 snap](/Users/serika/Developer/temp/endfield-demo-handoff-v3/dist/engine/sim/search.js:23) 当前存在这些具体缺口：

- 用施放占用时长替代命中偏移。当前普通战技、连携、终结技主要命中偏移分别是 **0.48、0.72、2.4 秒**，并非 0.8、1.2、3 秒；还有延迟段和重击绑定段。
- 忽略 `buffStart.until`、`buffRefresh`、`buffStack`。`buffEnd` 是模拟推进时才发现到期的日志时刻，不一定等于真实边界。
- 连携窗口刷新、终结技演出对窗口的延长，未完整反映到锚点。
- 能量锚点只看每人第一次满能采样；采样间隔至少 0.5 秒，满能后立即施放的事件可能完全漏掉。
- 缺少技力门槛、成员占用结束、冷却结束、关键普攻、敌人无敌窗口边界，以及各命中段对应的 `T−offset`。

建议模拟器输出带主体与精确时刻的事件、有效期变化和动作命中偏移。对动作 \(a\)，生成 `事件时刻−a的相关偏移` 及其边界两侧候选；保留约 10%–20% 的普通扰动或区间采样。不要把所有事件混成一个无类型时间集合。

另外，当前模拟器并非真正的 0.1 秒网格：顺序解码会产生 0.48、5.0175 秒等时刻，第二段入口却统一四舍五入。探针确认交接会改变得分。应统一合法决策时间域，或者明确把量化当成一次有成本、需要重新评估的变换。

**顺延修复可以保留，但应承认它搜索的是“释放时刻＋优先级”，而不是精确时间表。**

当前 6 秒修复保留了“不得早于请求时刻”，这一点符合上一轮建议；问题在于延迟可以很大，并且没有保留依赖关系：

- 后申请的同成员动作可能先执行；
- 连携可能使用另一轮触发窗口；
- 辅助动作与爆发链可能被拆开；
- 多个不同请求时间会解码成同一执行轨迹。

建议保留 `requestedT / actualT / delay / status / reason / triggerId`，分别测量延迟量、次序变化和依赖变化。对最终候选关闭修复重放，核对执行次数、时刻、错误和分数。[finish](/Users/serika/Developer/temp/endfield-demo-handoff-v3/dist/engine/sim/rotation.js:65) 已经重放，但没有强制拒绝不一致结果。

我检查的 100 份随机计划，执行轨迹严格重放未发现分数差异；这是有限验证，不能替代该断言。

**基准目前只支持“第二段能改善给定起点”，不支持“相同总预算下两段式更好”。**

[基准表](/Users/serika/Developer/temp/endfield-demo-handoff-v3/docs/reviews/planner-benchmark.md:19)里，30 秒的 A 在两个种子上都高于当时版本的 D。后来采用的无按住两段式，没有对应的同预算、同配置纯退火对照。

还有三处归因需要收回：

- 第二段允许插删、换类型和破坏重建，7%–15% 的增益不能直接归为“延迟和对齐”。
- 36 秒与 72 秒不是同一轨迹的两个截面。退火温度依赖总预算和评估上限，阶段切换点也不同；不能只解释为随机方差。
- “一次按住使分数大跌”证明该扰动可能破坏计划，不能证明按住变量普遍无用。增加变量后的提案分布和预算效率同样改变了。

建议先跑以下最小实验矩阵：

| 实验 | 固定条件 | 回答的问题 |
|---|---|---|
| 同一第一段检查点分叉：继续退火／只调时刻／完整局部搜索 | 相同起点、相同剩余墙钟预算 | 第二段是否值得替换继续退火；收益是否来自结构变化 |
| 纯退火／纯显式搜索／两段式 | 相同总预算、相同种子来源与目标 | 整体流程比较 |
| 第二段占比 0%、20%、40%、60%、100% | 其余参数固定 | 当前预算切分是否合理 |
| 关闭成组移动、破坏修复、锚点、自适应权重、档案、精调，逐项消融 | 固定基线与预算 | 各组件是否提供收益 |
| 修复上限 0、0.5、2、6 秒 | 完整执行状态统计 | 修复帮助可行性还是主要造成多对一编码 |

第一轮可用 **6 个机制不同的编队 × 30/60/90 秒窗口 × 20 个优化器种子**；参数选择后，在未参与调参的编队和场景上复验。编队应覆盖记录爆发、资源紧张、短触发窗口、持续伤害、控制切换等不同机制，而非只更换角色名字。

每次运行记录真正的历史最好值，保存 5/10/20/30/60 秒检查点，以及对应模拟次数。报告中位数、四分位数、最差分位数、配对相对增益和置信区间；长预算建立的参考值叫“最好已知值”。按实例汇总，避免把同一编队的多个种子当成多个独立业务实例。

预算依赖的温度和阶段切换需要单独比较：一条长运行的检查点用于 anytime 曲线，独立短预算运行用于评价部署配置。对应上一轮“多实例、多种子、目标质量与调用次数”的建议：[Hansen 等，2021／COCO](https://arxiv.org/abs/1603.08785)。上述实验规模是本题建议，不是论文规定。

**两段式有明显搜索偏置，但当前第二段并非固定骨架，因此不能笼统说第一段漏掉的结构永远修不回来。**

不带适当等待的最早可行解码，确实不能表达任意有益空闲。例如一个构造实例：A 的短增益现在可放，B 到第 10 秒才可放；最佳方案是 A 在第 9 秒、B 在第 10 秒。`A→B` 会把 A 提前浪费，`B→A` 又错过 B 的收益。现有层数等待也不能普遍表达这种等待。

当前第二段能把 A 移到第 9 秒，也能插删动作，所以这不是严格的永久盲区。真正的问题是**有限预算下的恢复难度**：

- 第一段按最早解码收益淘汰了“只有延迟才有价值”的动作组合。
- 第二段若要同时补回辅助、改变消费顺序、移动远处爆发，可能需要跨越明显的暂时降分。
- 当前时间邻近分组和最长约 8 秒的随机破坏，未必能一次触及相隔很远的依赖链。

只有第二段固定动作集合与次序时，缺失动作或错误骨架才会成为严格不可恢复限制。当前明确的表示限制则包括 0.1 秒时间域，以及未生成的动作类型；例如若允许主动切主控，当前两段都没有生成 `switch`。

建议第一段交付多个结构不同的方案，并加入空计划、资源保留方案、事件延迟方案；第二段允许整体插入或替换一条依赖链。保留原始束搜索时间表作为独立候选，因为转成顺序会丢失束搜索找到的等待。已复现一个 40 秒小实例，束搜索交接前为 49,654.8，重新最早解码后为 49,350.6。

还要注意，[autoPlan](/Users/serika/Developer/temp/endfield-demo-handoff-v3/dist/engine/sim/plan.js:34)本身是时间网格搜索：每个时刻每条分支只增加一个动作，无法直接构造同刻多成员施放；排序仍偏重近期伤害、能量比例和终结技数量。可以保留为种子生成器，但不能认为它已经可靠筛选了所有有潜力的结构。

COLIN 支持“找到计划后优化时间戳”这条建议，同时强调规划中时序与数值约束的耦合；它没有证明任意最早解码骨架足够好。对应上一轮“结构＋时间优化”的建议：[Coles 等，2012](https://kclpure.kcl.ac.uk/portal/en/publications/colin-planning-with-continuous-linear-numeric-change/)。

**乐观上界第一版可以不用求解器，但必须增加规则层接口。**

仅从模拟日志中的最大伤害和最大次数取值，不会得到有效上界。建议为当前编队输出以下保守包络：

| 信息 | 用途 |
|---|---|
| 每种动作最小占用、可靠的最小重复间隔 | 约束最多施放次数，必须覆盖减冷却、重置和免费替换阶段 |
| 所有可能伤害段及其最大次数、倍率、状态变量范围 | 覆盖直接伤害、追击、异常、延迟段及装备触发 |
| 属性、增益、敌人减伤等乘区的安全范围 | 构造单次伤害上界，不能只套当前面板 |
| 普攻最大频率及强化、重置路径 | 普攻基线不是普攻上界 |
| 伤害记录来源、比例、叠加与递归规则 | 覆盖记录爆发，避免漏项 |
| 初始资源、所有产能上限、最低消耗 | 第二版加入资源约束 |

第一版做一个很松但可审计的计算：

1. 忽略技力、能量、触发条件和全队互斥。
2. 若成员 \(i\) 每次主动动作至少占用 \(b_i>0\)，取总动作次数上界  
   \[
   N_i=1+\lfloor T/b_i\rfloor.
   \]
3. 给该成员每次动作都使用其最高单次直接伤害包络，再独立加上普攻和其他伤害来源的包络。互相矛盾的有利条件可以同时放宽，前提是各包络确实向上覆盖。
4. 单独放大记录伤害。

设排除副控直接普攻后的非记录伤害上界为 \(U_G\)，副控普攻上界为 \(U_N\)。若证明当前记录机制对每单位伤害最多额外产生 \(\beta\) 倍，且不递归记录爆发，则当前评分口径可用：

\[
U=(1+\beta)U_G+\beta U_N.
\]

这里的 \(U_N\) 不能漏掉，正是前面发现的间接贡献路径。当前 `S.ink` 单槽和 `inkBurst` 实现可用于建立这条证明；以后支持多重记录时必须重做。

不要要求所有动作完整结束于 \(T\)：末次动作跨窗口仍可能产生有效命中。对暂时无法证明包络的机制，返回“上界未覆盖”或无穷大，不能悄悄漏算。

第二版再用动作次数变量做 LP 松弛，加入总资源供给和成员容量的必要约束，继续放宽时序与触发。最大化问题必须读取松弛最优值或求解器有效上界，找到的一条高分松弛计划不算上界。对应上一轮“利用规则构造松弛界”的建议：[Fisher，1981](https://pubsonline.informs.org/doi/pdf/10.1287/mnsc.27.1.1)。

**补测和测量应围绕上述行为，先于新增算法。**

| 优先补测 | 必须锁住的预期 |
|---|---|
| 同刻资源竞争 | 两种次序正确区分；缓存结果等于直接评估 |
| 重启与档案更新 | 返回值不低于所有已验证候选；档案维护不影响历史最优 |
| 修复终态 | 6 秒边界、窗口截断、错误输入，每个动作都有唯一状态 |
| 阶段交接 | 秒数等待不丢失；规范化后重新评分；原始优秀计划保留 |
| 最终重放 | 无修复执行、时刻、动作数量、分数一致 |
| 预算 | 所有路径计费，每次模拟前检查硬上限 |

现有“不降分”测试还把优化后的未惩罚 `score.dps` 与优化前的惩罚分比较，可能掩盖退化；应该同时断言同口径分数与严格重放结果。

测量方面，至少补上各算子的改善幅度与耗时、请求计划到执行轨迹的重复率、同分率、修复延迟分布、历史最优发现阶段，以及缓存内存和 GC 时间。当前 `distinctRatio=evals/proposals` 混用了不同阶段的分子分母，探针中能超过 1，不能解释为“不同候选比例”。

我会按这个顺序推进：**先修缓存、历史最优、终态和预算；再统一评分与交接语义；然后做同一检查点的剩余预算分叉实验。** 这组实验会最直接地决定两段式是否值得继续投入。
